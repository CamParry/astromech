# Roadmap

One feature per file, split across four directories:

- `proposed/` — not started, and needs planning: an open decision, a missing
  design, or a trigger it waits for
- `planned/` — not started, and ready to build: the decisions are made and the
  work items are concrete
- `in-progress/` — started, partially done
- `completed/` — shipped

A file moves from `proposed/` to `planned/` once nothing in it waits on a
decision.

Status is encoded by the directory, so there are no status fields or emoji to go
stale. To add a feature, create a file in the right directory. To change status,
`git mv` the file — then run `pnpm run check:docs` and fix what it names.

The milestone is a field: every file outside `completed/` starts with
frontmatter holding `milestone: 1.0` or `milestone: later`. Changing a feature's
scope edits that line and moves nothing. After adding, moving or retagging a
file, run `pnpm run roadmap` to rewrite the progress index below. The
pre-commit hook rewrites it too, and `check:docs` fails when it is stale.

`check:docs` catches a **markdown link** to the old path from anywhere. It does
not catch a **backticked path**, because those go unchecked in `specs/`,
`roadmap/proposed/`, `roadmap/planned/`, `roadmap/in-progress/` and `roadmap/completed/`: planned work names files that do
not exist yet, and the frozen tree was accurate when written. So after a
`git mv`, grep for the old path as well. A reference in `completed/` is history
and should be left alone; one in a live document should be repointed.

A file in `completed/` is a frozen record of what shipped. Don't accumulate new
work in it: a defect found later gets its own file in `planned/`. A roadmap item
that fixes a defect names the class of defect (where else it can occur), not
only the instance.

`backlog.md` holds unscheduled work that belongs to no single feature. The `docs`
skill has the full contract for all of this.

## 1.0 order

Decided on 2026-10-13. A feature is in 1.0 when it fixes a correctness,
security or data-loss defect; when it changes stored data, config or the plugin
API in a way that breaks a site, which costs nothing while no sites exist; or
when a site cannot be built without it. Anything that only adds can ship in a
1.x release and is tagged `later`.

Items are named by file, without a path, so a move needs no edit here. Where
only part of a file is in 1.0, the part is named, and the rest moves to a
`later` file when the work is picked up.

shorter-project-docs, affected-checks, then scripts-review, go before item 3: none changes
product code, and every change after them reads less and waits less.

**Must, in this order:**

1. admin-save-and-label-defects.
2. schema-engine-defects: the rebuild ordering that deletes child rows. Its D1
   item waits on d1-migrations-run-as-one-batch.
3. create-skips-field-pipeline: the open item.
4. undeclared-field-keys: a save keeps the stored values of a renamed or
   removed field. Split from field-rename-command, which is `later`.
5. relationship-index-defects, with the `kind` to `type` rename from
   naming-conventions, since both change the `relationships` table.
6. drafts and permissions, on two branches at once. Drafts also takes the
   column classification from derive-from-one-source, since it rewrites those
   copies.
7. history.
8. schedules.
9. hooks.
10. editor-locking.
11. field-value-query-indexing.
12. locale-settings.
13. notifications-channels-and-events: `defineNotification`, rows holding
    `type` and `params`, the `ctx.notify` signature and the email channel. The
    emitters can follow.
14. admin-widgets: the `Field | Layout | Widget` union, `defineWidget` and the
    edit-screen areas. The dashboard grid is `later`.
15. cli-commands: the defects, `db:migrate`, `defineCommand` with plugin
    commands, and the shared flags. Generated commands, `prune`, `doctor` and
    `media:*` are `later`.
16. lint-and-type-checks: the published-types check only.
17. create-astromech, last, so its templates use the final config.

**Should, if time allows, in this order:** two-factor-and-passkeys without
passkeys (confirming a password, TOTP and the per-role requirement), api-keys,
user-suspension, audit-trail, ordered-and-nested-entries, conditional-fields,
page-caching, sidebar-groups.

Every other planned file is `later`.
