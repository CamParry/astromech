# 0094 — core tests share a module graph

**Date:** 2026-08-24
**Status:** accepted

Core's vitest run spent 329 seconds of worker CPU importing modules against 122 seconds running test bodies, because vitest's default `forks` pool builds a fresh module graph for every one of the 222 files, so the suite moves to `pool: 'threads'` with `isolate: false` and a `tests/_support/isolated-tests.ts` list of the files that opt back into per-file isolation. Threads alone (isolation kept, no behaviour change at all) took the core run from 61s to 48s; dropping isolation as well took it to 32s, and an alternating four-run A/B on a busier machine held the same shape (72s and 78s against 48s and 58s). Six files failed without isolation, every one of them a `vi.mock` of a module another file had already imported into the shared graph, which is the failure vitest's own guidance predicts; the list is widened to the 39 files that mock a module, stub a global or write `globalThis.__astromech`, and `tests/isolation-list.test.ts` fails when the list and the files that actually do those things disagree, so it is enforced rather than remembered. The mechanical rule beats naming only the six that happen to fail today, because a leaked mock can as easily make an unrelated test pass for the wrong reason as fail. Vitest's documented convention of a `*.non-isolated.test.ts` suffix loses because it inverts the default the wrong way round for a suite where 183 of 222 files are safe. `deps.optimizer.ssr` was measured and rejected: pre-bundling made the run slower (65s), not faster. Folding the three package suites into one root workspace was built and rejected too: it matched three separate invocations to within a second (46.5s against 47.5s) and broke `tests/integrations/cloudflare/d1-local-emulation.test.ts`, which discovers `packages/astromech/wrangler.jsonc` from the process working directory. schema-engine and assistant keep their configs untouched, being 1.5s and 0.8s.
