# 0093 — barrels are entry points, not navigation

**Date:** 2026-08-24
**Status:** accepted

A re-export barrel gives an outside caller one name for a package and is not how a package talks to itself, so barrels survive only where something outside reads them (`src/exports/`, plus the two under `src/admin/components/` the Astro integration aliases for `astromech/ui` and `astromech/ui/fields`) and the other seventeen go, every import naming the defining file; an `index.ts` holding real code is not a barrel and stays. The barrels had already lost in the code: 93% of local imports bypassed them, `database/`, `cron/` and `config/` had no importers at all, `admin/hooks/index.ts` closed a cycle with `use-entry-form.ts`, and the two `astromech/ui` barrels' module-scope `assertSingleUiInstance()` made `sideEffects: false` untrue (now an array naming the guard, the admin entry's registrations, the stylesheets and tsup's shared chunk, with `admin/main.tsx` calling the guard itself). The import-time argument that Vite's performance guide, TkDodo and Atlassian make did not reproduce here — vitest's aggregate module-import time stayed inside its run-to-run variance on both sides — so the reasons above carry the change alone. Keeping module barrels as intra-package boundaries loses because nothing enforced barrel-only entry and the browser boundary needs the opposite (deep imports of pure leaves); `src/types/index.ts` is kept because its 359 imports are type-only and erase at compile time; the real-code `index.ts` files are not renamed, the lint rule carrying their list instead.
